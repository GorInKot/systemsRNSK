# Перенос заявок ЦУС / SIM / 1С:ПБиОТ на портал

Документ для того, кто переносит модуль заявок «ЦУС», «SIM-карта», «Удержание за
перелимит связи» и «1С:ПБиОТ» в портал с другой архитектурой (не FastAPI +
SQLAlchemy + PostgreSQL, как здесь). Остальные системы каталога (`account`, `mail`,
`pkzi`, `vipnet`, `ksed`, `vkd`, `terminal`, `ai_lab`) устроены точно так же — этот
документ можно использовать как образец и для них.

## Что реально нужно перенести

Из всего репозитория для работы этих 4 заявок нужны только три вещи:

1. **Уже готовые бланки с метками** — обычные `.docx`/`.xlsx`, которые открываются в
   Word/Excel как есть, просто вместо значений в нужных ячейках/абзацах стоит текст
   `{{TOKEN}}`:
   - `backend/app/data/templates/tsus.xlsx`
   - `backend/app/data/templates/sim.docx`
   - `backend/app/data/templates/sim_deduction.docx`
   - `backend/app/data/templates/c1_pbiot.docx`
2. **Функция подстановки** — `backend/app/services/templates.py:fill_template`.
   Тривиально переносится на любой стек: открыть файл как ZIP, найти нужную XML-часть,
   заменить `{{TOKEN}}` на значение, записать обратно.
3. **Таблица токенов** — какое поле анкеты сотрудника подставляется в какую метку.
   Она вся здесь, в разделах ниже, и продублирована в
   `backend/app/services/systems_catalog.py` функциями `_tsus_map_values`,
   `_sim_map_values`, `_sim_deduction_map_values`, `_c1_pbiot_map_values`.

Всё остальное в репозитории (`build/build.py`, исходные бланки в `types/`,
FastAPI-роуты, SQLAlchemy-модель `EmployeeProfile`) нужно только на **этой** системе
и только если понадобится **пересобрать** шаблон заново (например, заказчик прислал
исправленный бланк). Для повседневной работы модуля на портале это не требуется —
готовых файлов из п. 1 достаточно.

## Как работает подстановка (`fill_template`)

```python
TOKEN_RE = re.compile(r"\{\{([A-Z0-9_]+)\}\}")

def fill_template(key, values, text_parts):
    # 1. открыть шаблон (.docx/.xlsx) как ZIP-архив
    # 2. для каждой части архива из text_parts (см. ниже) —
    #    декодировать как UTF-8 и заменить {{TOKEN}} на values.get(TOKEN, "{{TOKEN}}")
    #    (нет значения — метка остаётся как есть, это осознанное поведение:
    #    так помечены поля, которые заполняются от руки)
    # 3. остальные части архива скопировать без изменений
    # 4. вернуть новый ZIP как есть — это готовый .docx/.xlsx
```

`text_parts` — какая часть архива внутри `.docx`/`.xlsx` содержит текст:

| Тип файла | text_parts | Что это |
|---|---|---|
| `.docx` | `{"word/document.xml"}` | основное тело документа |
| `.xlsx` (после пересборки openpyxl) | `{"xl/worksheets/sheet1.xml"}` | единственный лист (лишние листы при сборке удаляются, остаётся один → всегда `sheet1.xml`) |

Про сжатие ZIP-частей можно не думать — стандартная библиотека `zipfile` (или её
аналог в любом другом языке) сама разбирается со сжатым/несжатым содержимым при
чтении. Разделение на «сжато/не сжато» в `build/build.py` (`mixed_zip`) — это костыль
для **старого** прототипа (`index.html`), где подстановку делал самодельный
JS-движок без доступа к inflate/deflate в браузере. На сервере (и на портале) это
не нужно вообще — обычный `zipfile`/`ZipArchive`/что угодно справится с любым
файлом из п. 1 «как есть».

Экранирование при подстановке — обычный XML-escaping (`& < > "`), см.
`_xml_escape` в `templates.py`. Больше никакой магии нет.

## Что нужно реализовать заново на портале

Логика вокруг подстановки (не самой подстановки — она портируется как есть):

1. **Откуда брать данные** — на этой системе профиль сотрудника лежит в таблице
   `employee_profiles` (SQLAlchemy). На портале это будет какой-то свой источник
   (LDAP/AD, другая БД, другой профиль пользователя) — нужно на входе собрать
   такой же плоский словарь `{"full_name": ..., "department": ..., ...}`, какой
   строит `profile_to_dict()` здесь.
2. **Проверка полноты анкеты** — у каждой заявки есть список обязательных полей
   (`need`, см. таблицы ниже). Если что-то не заполнено — заявку не формируем,
   показываем сотруднику, чего не хватает. Здесь это `System.missing_fields()`.
3. **Выбор действия на карточке** — только у 1С:ПБиОТ есть выбор одного из двух
   вариантов прямо на карточке заявки (`choice_field`/`choice_options`, см. ниже) —
   это отдельный параметр запроса, не часть анкеты.
4. **Имя итогового файла** — `file_name` в описании каждой системы ниже.

## ЦУС / СЭИД

- Шаблон: `tsus.xlsx` (лист «ЗаявкаЦУС», данные — строка 9).
- Файл результата: `Заявка_ЦУС_{ФИО}.xlsx`
- Обязательные поля анкеты (`need`): `full_name`, `position`, `email`,
  `account_name`, `pkzi_name`, `seid_role` (новое поле — «роль в ИР СЭИД», нигде
  больше не используется, только здесь).
- Выбора действия на карточке нет.

| Токен | Поле анкеты | Комментарий |
|---|---|---|
| `{{FIO}}` | `full_name` | |
| `{{POST}}` | `position` | |
| `{{EMAIL}}` | `email` | |
| `{{ACCOUNT}}` | `account_name` | |
| `{{CERT}}` | `pkzi_name` | имя ключа ПКЗИ |
| `{{ROLE}}` | `seid_role` | роль в ИР СЭИД, текстом |

Ячейка D9 («ОГ», наименование организации) в шаблоне уже содержит фиксированный
текст `ООО "РН-СтройКонтроль"` — не токенизирована и не подставляется, потому что
портал ведёт анкеты только сотрудников этого общества. Если на новом портале
общество может быть другим — эту ячейку нужно тоже токенизировать (в `build.py`
она сейчас сознательно не тронута).

## SIM-карта (выдача / переоформление)

- Шаблон: `sim.docx`
- Файл результата: `Заявка_СИМ_{ФИО}.docx`
- Обязательные поля: `full_name`, `department`, `position`, `manager_full_name`,
  `manager_position`.
- Выбора действия на карточке нет.

| Токен | Поле анкеты | Комментарий |
|---|---|---|
| `{{FIO}}` | `full_name` | таблица, строка «Фамилия, имя, отчество» |
| `{{PODR}}` | `department` | таблица, строка «Структурное подразделение» |
| `{{POST}}` | `position` | таблица, строка «Должность Работника» |
| `{{EMAIL}}` | `email` | таблица, строка «Электронная почта» |
| `{{FIO_SIGN}}` | `full_name` | подпись работника под согласием на обработку ПДн |
| `{{RUK_POST}}` | `manager_position` | подпись «Согласовано»: должность руководителя |
| `{{RUK_FIO}}` | `manager_full_name` | подпись «Согласовано»: ФИО руководителя |

**Сознательно не заполняется** (в исходном бланке для этого нет ни чекбоксов, ни
отдельных полей в анкете — заполняется от руки на распечатанном бланке):
паспортные данные, дата рождения, адрес регистрации, наличие УЗ на Госуслугах,
тип/размер SIM-карты, переоформление на юр./физ. лицо, номер телефона, дата и
собственноручная подпись.

**Важно при переносе**: обращения к абзацам и ячейкам в `build_sim()`
(`build/build.py`) идут **по номеру** (`doc.paragraphs[11]`, `doc.tables[0].rows[0]`
и т.д.) — это позиции в конкретном файле `types/Заявка СИМ-карта.docx`. Если бланк
на портале будет другим файлом (даже слегка отредактированным в Word) — номера
абзацев/строк могут не совпасть. Переносить нужно **готовый** `sim.docx` с уже
расставленными метками (см. «Что реально нужно перенести»), а не пересобирать его
заново из блан­ка без крайней необходимости.

## Удержание за перелимит связи

- Шаблон: `sim_deduction.docx`
- Файл результата: `Заявление_Удержание_СИМ_{ФИО}.docx`
- Обязательные поля: `full_name`, `department`, `position`.
- Выбора действия на карточке нет.

| Токен | Поле анкеты | Комментарий |
|---|---|---|
| `{{POST}}` | `position` | строка «от ___» — должность |
| `{{PODR}}` | `department` | вторая строка — подразделение |
| `{{FIO}}` | `full_name` | третья строка — ФИО полностью |

Значения выводятся подчёркнутыми (имитация заполненной от руки линии бланка) —
это сделано в `build.py` хелпером `underline_token`, а не в `fill_template`: сам
токен — обычный текст, подчёркивание — форматирование run'а в уже готовом шаблоне.
На портале это не требует отдельной логики — подчёркивание уже «зашито» в файл
`sim_deduction.docx`, подставляется как обычный текст.

Номер телефона и строка с датой/подписью/расшифровкой подписи — от руки (нет
соответствующих данных в анкете).

## 1С:ПБиОТ

- Шаблон: `c1_pbiot.docx`
- Файл результата: `Заявка_1С_ПБиОТ_{ФИО}.docx`
- Обязательные поля: `full_name`, `department`, `position`, `manager_full_name`,
  `manager_position`, `manager_phone`, `account_name`, `pkzi_name`.
- **Выбор действия на карточке** (`choice_field="c1_pbiot_action"`): один из двух
  вариантов, не часть анкеты, а параметр запроса на генерацию:
  - `"предоставить полномочия"` (по умолчанию)
  - `"прекратить доступ"`

| Токен | Значение | Комментарий |
|---|---|---|
| `{{CHK_GRANT}}` | `☒`, если выбрано «предоставить полномочия», иначе `☐` | |
| `{{CHK_REVOKE}}` | `☒`, если выбрано «прекратить доступ», иначе `☐` | |
| `{{FIO}}` | `full_name` | |
| `{{PODR_POST}}` | `department + ", " + position` | склеены через запятую |
| `{{RUK}}` | `manager_full_name + ", " + manager_position + ", " + manager_phone` | |
| `{{EMAIL}}` | `email`, либо «в процессе оформления», если `no_email` | |
| `{{PHONE}}` | `phone` | |
| `{{ACCOUNT}}` | `account_name` | |
| `{{CERT}}` | `pkzi_name` | |
| `{{RUK_FIO_SIGN}}` | `manager_full_name` | строка согласования в конце бланка |

Фиксированный текст (не токенизирован, вписан напрямую в шаблон): название
организации «ООО «РН-СтройКонтроль»» и значение «Нет» в столбце «Ограничения
доступа к данным» (по умолчанию — без ограничений).

**Сознательно не заполняется**: список ролей (23 пункта в отдельной таблице — в
бланке под них нет ни чекбоксов, ни текстовых полей вообще, отмечаются от руки),
подпись работника, дата, ограничения по конкретным подразделениям, тип
подключения ЕКТС/не ЕКТС, согласующие подписи (ИБ ОГ / Владелец Ресурса / ИБ РН).
Изначально была попытка добавить множественный выбор ролей в анкету и вписывать
их в бланк текстом — отказались от этой идеи, поэтому в текущей версии
`EmployeeProfile` соответствующего поля нет.

**Важная особенность бланка**: чекбоксы действия в исходном файле — не текстовые
символы `☐`/`☒` (как в `pkzi.docx`/`vkd.xlsx`), а шрифтовый символ Wingdings,
встроенный в XML как `<w:sym w:font="Wingdings" w:char="F0A8"/>` внутри `<w:r>`
без текста. Штатная подстановка `{{TOKEN}}` работать не может — символа-метки там
попросту нет, есть только `<w:sym>`. Решение — хелпер `sym_to_token()` в
`build.py`: на этапе сборки удаляет `<w:sym>` из run'а и вставляет вместо него
обычный текст-метку. Это разовая операция при подготовке шаблона; сам
`c1_pbiot.docx` в `app/data/templates/` уже содержит обычный текст `{{CHK_GRANT}}`
/`{{CHK_REVOKE}}`, никакого Wingdings там больше нет — при переносе **готового**
файла эта деталь не всплывёт. Важна она только если бланк придётся токенизировать
заново из другого исходника с той же особенностью.

Как и в SIM-карте, обращения в `build_c1_pbiot()` идут по номерам таблиц/строк
конкретного файла `types/Заявка 1С ПБиОТ.docx` — при пересборке из другого файла
номера могут не совпасть.

## Проверка после переноса

В `backend/tests/test_templates.py` есть тесты на все 4 системы
(`test_tsus_tokens_are_replaced`, `test_sim_tokens_are_replaced`,
`test_sim_deduction_tokens_are_replaced`, `test_c1_pbiot_marks_the_chosen_checkbox`) —
на каждый шаблон отдельно, без БД и без API, только вызов `fill_template` с
тестовыми значениями и проверка, что `{{` не осталось в результате. Их удобно
взять образцом для проверки на портале: собрать словарь значений → вызвать
подстановку → открыть результат `python-docx`/`openpyxl` (или просто в Word/Excel)
и убедиться, что данные на месте и меток `{{...}}` не осталось там, где они не
должны остаться намеренно (см. «сознательно не заполняется» по каждой системе).
