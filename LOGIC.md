# Логика сервиса заявок на доступы

Документ фиксирует текущую реализацию `index.html` — как всё устроено и куда вносить правки.

## Назначение

HTML-сервис для оформления заявок на доступы к корпоративным системам. Лежит на
сетевом хранилище, открывается двойным кликом (`file://`). Сотрудник **один раз
заполняет анкету** (все поля всех заявок), затем на вкладке «Заявки» формирует
любой документ (Word/Excel) в один клик — данные подставляются из анкеты.

## Ограничения и принятые решения

| Требование | Решение |
|---|---|
| Один HTML-файл, без зависимостей | Весь HTML+CSS+JS в `index.html`, без CDN; шаблоны встроены сборкой (base64) |
| Настоящие Word/Excel без библиотек | Заполняются реальные `.docx/.xlsx`: собственный ZIP-движок меняет метки `{{TOKEN}}` в несжатых частях архива |
| Заполнять данные один раз | Единая **анкета** (профиль сотрудника); каждая заявка берёт из неё нужные поля |
| Отдельный файл на каждую заявку | Кнопка «Создать и скачать» формирует отдельный документ из анкеты |
| Скачивание из браузера | `Blob` + `<a download>` |
| Хранение в JSON | Анкета в `localStorage` (`anketa-v1`) + Экспорт/Импорт JSON (один сотрудник = один файл) |

## Поток работы сотрудника

1. Открывает файл → вкладка **«Анкета»**: заполняет поля (личные данные,
   руководитель, параметры заявок). Данные **автосохраняются** в `localStorage`
   на каждый ввод; редактируются в любой момент.
2. Переходит на вкладку **«Заявки»** → карточки систем. Если нужных полей
   не хватает, карточка подсказывает, что дозаполнить в анкете.
3. Нажимает **«Создать и скачать»** → файл заявки формируется из анкеты и
   скачивается.
4. Экспорт/Импорт JSON — перенос анкеты между браузерами/ПК.

## Архитектура кода (`index.html`)

Вся предметная логика вынесена в конфиг — правки идут туда, а не в код.

### `SYSTEMS` — список систем (главный конфиг)

Массив объектов, по одному на систему. **Порядок массива = порядок карточек
в сетке** (рекомендованная последовательность оформления, без блокировки):
УЗ → Почта и ПКЗИ → остальные. Поля объекта:

- `id` — уникальный идентификатор карточки.
- `title`, `icon`, `desc` — отображение на карточке.
- `hl` — выделение карточки цветом `rgb(247,191,106)` (обязательные первые
  заявки: УЗ, Почта, ПКЗИ).
- `template` — ключ встроенного шаблона в `window.TEMPLATES`, либо функция
  `d=>ключ` (выбор шаблона по данным, напр. офис в УЗ); `null` = карточка
  неактивна («🛠 Шаблон в подготовке»); заглушки — хелпер
  `stub({id, title, icon, desc})`.
- `textParts` — части шаблона-архива, в которых меняются метки
  (docx — `word/document.xml`, xlsx — `xl/worksheets/sheet1.xml`).
- `need` — массив имён полей **анкеты**, без которых заявку не сформировать;
  пока не заполнены — кнопка неактивна, карточка показывает, чего не хватает.
- `fileName(d)` — имя скачиваемого файла по данным анкеты `d`.
- `mapValues(d)` — данные анкеты → значения меток `{{TOKEN}}` шаблона.

`d` в `fileName/mapValues` — это профиль анкеты `withDefaults(profile)`
(канонические имена полей, см. `ANKETA`). **Добавить систему** = добавить
объект в `SYSTEMS` (и, при новом шаблоне, сборщик в `build.py`); поля берутся
из анкеты, при нехватке — расширить `ANKETA`. Родственные карточки на одном
бланке делает фабрика (`makePkzi` — ПКЗИ и VipNet/ДП, различаются `actionField`).

### Анкета (`ANKETA`) — единая форма всех полей

`ANKETA` — массив секций `{title, fields:[…]}`; `ANKETA_FIELDS` — плоский
список. Поле:

```js
{ name:'fio', label:'ФИО', type:'text', wide:true, placeholder:'...' }
```

- `type`: `text` (по умолч.), `select` (с `options:[]`), `checkbox`,
  `checks` (группа чекбоксов `options:[]`, значение — массив; напр. наимен. ВКД).
- `default`: значение/функция; подставляется в незаполненные поля через
  `withDefaults` (поля-выборы всегда «заполнены»; `checks` по умолч. — `[]`).
- `wide`: поле на всю ширину секции.
- `checkbox` с `disables:'имя'` блокирует связанное поле (напр. «нет E-mail»).

Имена полей анкеты **канонические** и общие для всех заявок (`fio`, `podr`,
`account_name`, `pkzi_name`, `fio_ruk`, `vkd_action`, `vdr` …). `mapValues`
каждой системы раскладывает их по своим меткам `{{TOKEN}}`.

**Не в анкете (на карточке или зашито в код):** действия ПКЗИ/VipNet
выбираются выпадающим списком прямо на карточке заявки (`SYSTEMS[].choice =
{field, options}`, выбор хранится в `cardChoice[id]`, подставляется в
`genRequest`); срок ПКЗИ — 365 дней со дня формирования; объём почтового
ящика — 1 Гб; обоснование доступа (КСЭД, ВКД) — `ACCESS_REASON` в коде.

### Генерация файлов — заполнение реальных шаблонов

Готовые заявки формируются **заполнением настоящих `.docx/.xlsx`** из [types/](types/)
(точная копия официальной формы), а не пересозданием вёрстки.

- `genRequest(id)` → `downloadRequest(sys, withDefaults(profile))` — берёт
  встроенный шаблон, заполняет через `fillTemplate(...)`, скачивает как
  `sys.fileName(data)`.
- `fillTemplate(b64, values, textParts)` — ZIP-движок: меняет метки `{{TOKEN}}`
  в несжатых частях (`textParts`) и копирует остальные «как есть». Без
  deflate/inflate.

### Сборка шаблонов — `build/build.py`

Итоговый `index.html` самодостаточен, но шаблоны в него **встраиваются сборкой**:

1. `build.py` токенизирует каждый шаблон (заполняемые ячейки → `{{TOKEN}}`,
   имена токенов совпадают с `mapValues` в `index.html`).
2. Пересобирает в ZIP: `document.xml` — **STORED** (несжато, чтобы браузер менял
   метки), остальное — DEFLATE (копируется без распаковки).
3. base64 и вставляет в `index.html` между `<!--TEMPLATES:START/END-->`.

Запуск: `python3 build/build.py` (нужны `python-docx` и `openpyxl` — только
для сборки). С `file://` через `fetch` шаблоны не грузятся, поэтому base64
встроен в HTML.

### Статус шаблонов

- **Готовы:** Лаборатория ИИ (`ai_lab`), Ключевая информация ПКЗИ (`pkzi`),
  VipNet / Деловая почта (`vipnet`), Терминальный сервер (`terminal`),
  Учётная запись (`account` — головной / `account_fil` — филиал),
  Почтовый ящик (`mail_fil` — филиал), КСЭД (`ksed`), ВКД (`vkd`).
- **В подготовке** (кнопка неактивна, статус «🛠 Шаблон в подготовке»):
  SAP (`sap`), 1С (`c1`).

Заявки из `ШаблонОбщий.xlsx` (терминал, УЗ, почта) собираются общим хелпером
`build_sheet(sheet, cells, out_name)`: оставляет в книге один лист, вписывает
метки в заданные ячейки, пересобирает. openpyxl пишет строки inline, поэтому
текстовая часть для замены меток — `xl/worksheets/sheet1.xml` (не
sharedStrings). № заявки, даты и подписи бланков — от руки. Коллективные
бланки (таблица на несколько работников) оформляются на одного человека:

- **Терминальный сервер** (`terminal`, лист «6.Терминальный сервер»): бланк «на
  изменение правил работы МЭ», группа `AD_RNSK_TRM_Users_WS`; D14 — ФИО,
  E14 — наименование ПКЗИ.
- **Учётная запись** (лист «2.УЗ» головной / «УЗ (Филиал)»): поле «Офис»
  выбирает шаблон (`template` — функция от данных). Головной — домен
  rosneft.ru напрямую, бланк заодно **просит создать почтовый ящик** (E12 —
  фикс. текст), поэтому у головного отдельной заявки на почту нет; приказ о
  приёме (`showIf` — только головной) вписывается в основание D12. Филиал —
  через СИБИНТЕК (группа `PKZI_EKTS_EX_Clients_CDC`). WORKER (ФИО/должность/
  телефон одной строкой), PODR — подразделение.
- **Почтовый ящик** (`mail_fil`, лист «ПЯ (Филиал)») — **только филиал**
  (у головного почта в заявке УЗ): WORKER, SIZE (объём ящика — всегда `1` Гб,
  зашит), PODR, ACCOUNT (имя УЗ в домене), CERT (имя сертификата ПКЗИ),
  RUK (руководитель).
- **КСЭД** (`ksed`, лист «4.КСЭД») — «Управление доступом», тип
  «Первоначальный доступ» (зашит в бланке, как ДЕЙСТВИЕ/ПРОФИЛЬ/СРОК). Строка
  таблицы на одного: FIO, ACCOUNT (УЗ), EMAIL, CERT (ПКЗИ), PODR (СП), POST,
  REASON (обоснование — `ACCESS_REASON`, зашито); колонки «принимающий права» —
  для передачи прав, пусты.

**ВКД** (`vkd`) — отдельный файл `types/Заявка ВКД.xlsx` (один лист), сборщик
`build_vkd` (не через `build_sheet`). Блок «Действия с учётной записью» —
чекбоксы ☑/☐ (выбор одного из пяти, как в ПКЗИ): в сборке символ в начале
ячейки заменяется меткой `{{CHK_*}}`, текст пункта сохраняется. Таблица
пользователей — 4 блока по 6 строк; **в исходнике вшиты три реальных
сотрудника-примера** — сборщик их вычищает (блоки 2–4 обнуляются), заполняется
первый блок (строки 15–20) на одного человека: VDR (наименование ВКД —
чекбоксы `vdr`, одно или несколько, объединяются через запятую), FIO,
EMAIL, PHONE (для SMS-кода), ACCOUNT (имя УЗ с доменом), KEY (имя ключа
ПКЗИ-КТ), REASON (основание — `ACCESS_REASON`, зашито). «Компания» и срок
«☑До срока действия ВКД» —
значения бланка по умолчанию; подписи владельца ВКД, ИБ, руководителя — от руки.

ПКЗИ: один бланк на четыре действия — выбранное **на карточке** действие
ставит ☒ в нужный чекбокс шаблона (чекбоксы w14:checkbox разворачиваются в
плоский текст ☒/☐ при токенизации; интерактивным остаётся только
«Переименование»). Действия поделены между карточками: `pkzi`
(`actionField:'pkzi_action'`) — первичная генерация и продление сертификата,
`vipnet` (`actionField:'vipnet_action'`) — абонентский пункт и добавление
контактов «VipNet»; выбор — выпадающий список на карточке (`choice`), не в
анкете. Из анкеты берутся подразделение, данные пользователя (`fio`/`post`/
`phone`) и руководителя СП, e-mail, имя сертификата (`pkzi_name`), приказ.
Срок использования вычисляется автоматически: сегодня → +365 календарных дней
(`ruDateOf`). Подписи и тип ПКЗИ («КТ») — по бланку.
Обе карточки собирает фабрика `makePkzi`. Нюансы:

- телефоны дополняются пробелами до 28 знаков (`padTo`, ширина телефона в
  исходном шаблоне), чтобы подписи «Телефон … Подпись» строкой ниже не
  съезжали; в шаблоне на этих метках `xml:space="preserve"` (см. `build.py`);
- приказ вводится как «№ приказа, дата» (напр. `86-к, 11.12.2020`), «от»
  подставляет код (`orderFmt`) → в заявке «Приказ № 86-к от 11.12.2020»;
- чекбокс «нет E-mail» блокирует поле E-mail; в заявку тогда пишется
  «в процессе оформления»;
- имя сертификата — с новой строки после «Имя сертификата:», подчёркнутым
  («на линии»); пустое значение → линия «___» под заполнение от руки.

### Хранение и перенос данных

- `profile` — объект `{ поле: значение }` (канонические имена анкеты),
  автосохраняется в `localStorage` под ключом `anketa-v1`.
- `withDefaults(profile)` — профиль + значения по умолчанию для незаполненных
  полей (для генерации и проверки `need`).
- `exportJson()` / `importJson()` — выгрузка/загрузка анкеты одним JSON-файлом
  (`анкета_<ФИО>.json`). **localStorage привязан к браузеру/ПК**; перенос —
  через экспорт/импорт.

## Текущий набор систем

Порядок карточек: **Учётная запись, Почтовый ящик, ПКЗИ, VipNet ДП, КСЭД,
SAP, 1С, ВКД, Терминальный сервер, Лаборатория ИИ**.

- **Готовы:** Учётная запись, Почтовый ящик, ПКЗИ, VipNet ДП, КСЭД, ВКД,
  Терминальный сервер, Лаборатория ИИ.
- **Заглушки** («Шаблон в подготовке»): SAP, 1С — исходных бланков пока нет.

Гейтинга (блокировки карточек по зависимостям) нет — последовательность
задаётся порядком в сетке и цветовым выделением обязательных первых заявок
(УЗ, Почта, ПКЗИ). Готовность карточки к формированию определяется полем `need`
(нужные поля анкеты заполнены).

## Две вкладки: Анкета / Заявки

Над вкладками — строка с «Загрузить пример» / «Экспорт JSON» / «Импорт JSON»
(анкета одного сотрудника) и индикатор состояния (`anketaState`).

### Анкета (`#pane-anketa`, основная)

Форма `ANKETA` по секциям (`renderAnketa`). Автосохранение: `form.oninput/
onchange = saveAnketa` (не `addEventListener` — форма не пересоздаётся, слушатели
не должны накапливаться). `saveAnketa` пишет `profile`, перерисовывает сетку
заявок и индикатор. «нет E-mail» блокирует поле E-mail.

### Заявки (`#pane-req`)

Сетка карточек всех систем (`renderGrid`). Для каждой: `missing =
need.filter(k => !withDefaults(profile)[k])`. Пусто → кнопка «Создать и скачать»
(`genRequest`); есть недостающие → кнопка неактивна и подсказка «Дозаполните в
анкете: …» (метки из `FIELD_LABEL`); нет шаблона → «🛠 Шаблон в подготовке».

### Реализация

- `switchTab(name)` переключает `.tab`/`.pane` по `data-tab` / `pane-<name>`.
- `render()` = `renderAnketa()` + `renderGrid()` + `updateState()`.
- `fieldControl(f, val)` — общий построитель `input`/`select` для анкеты.
