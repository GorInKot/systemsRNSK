# Логика сервиса заявок на доступы

Документ фиксирует текущую реализацию `index.html` — как всё устроено и куда вносить правки.

## Назначение

HTML-сервис для оформления заявок на доступы к корпоративным системам. Лежит на
сетевом хранилище, открывается двойным кликом (`file://`). Новый сотрудник видит
чек-лист систем, заполняет заявки и по каждой скачивает готовый файл (Word/Excel).

## Ограничения и принятые решения

| Требование | Решение |
|---|---|
| Один HTML-файл, без зависимостей | Весь HTML+CSS+JS в `index.html`, без CDN; шаблоны встроены сборкой (base64) |
| Настоящие Word/Excel без библиотек | Заполняются реальные `.docx/.xlsx`: собственный ZIP-движок меняет метки `{{TOKEN}}` в несжатых частях архива |
| Отдельный файл на каждую заявку | При «Сохранить и скачать» формируется отдельный документ |
| Скачивание из браузера | `Blob` + `<a download>` |
| Хранение в JSON | `localStorage` (браузер с `file://` не пишет на диск молча) + Экспорт/Импорт JSON |

## Поток работы сотрудника

1. Открывает файл → видит **чек-лист** карточек систем со статусом
   «● Не оформлено / ✓ Оформлено».
2. Нажимает **«Заполнить»** → открывается **модальное окно** с полями.
3. Заполняет поля (обязательные проверяются) → **«Сохранить и скачать»**.
4. Состояние сохраняется в `localStorage`, файл заявки **скачивается автоматически**.
5. Заявку можно **«Изменить»** или **«Скачать файл»** повторно.
6. Прогресс отображается как «Оформлено: N из M».

## Архитектура кода (`index.html`)

Вся предметная логика вынесена в конфиг — правки идут туда, а не в код.

### `SYSTEMS` — список систем (главный конфиг)

Массив объектов, по одному на систему. **Порядок массива = порядок карточек
в сетке** (рекомендованная последовательность оформления, без блокировки):
УЗ → Почта и ПКЗИ → остальные. Поля объекта:

- `id` — уникальный идентификатор (ключ в `localStorage`).
- `title`, `icon`, `desc` — отображение на карточке.
- `hl` — выделение карточки цветом `rgb(247,191,106)` (обязательные первые
  заявки: УЗ, Почта, ПКЗИ).
- `template` — ключ встроенного шаблона в `window.TEMPLATES`, либо функция
  `d=>ключ` (выбор шаблона по данным, напр. офис в УЗ); `null` = карточка
  неактивна («🛠 Шаблон в подготовке»); заглушки — хелпер
  `stub({id, title, icon, desc})`.
- `textParts` — части шаблона-архива, в которых меняются метки
  (docx — `word/document.xml`, xlsx — лист/sharedStrings).
- `fields` — массив полей модального окна (см. ниже).
- `fileName(d)` — имя скачиваемого файла по данным `d`.
- `mapValues(d)` — данные полей → значения меток `{{TOKEN}}` шаблона.

**Добавить систему** = добавить объект в массив `SYSTEMS` (и, при новом
шаблоне, сборщик в `build.py`). Родственные карточки на одном бланке делаются
фабрикой (см. `makePkzi` — ПКЗИ и VipNet/ДП).

### Описание поля (`fields[]`)

```js
{ name:'fio', label:'ФИО', type:'text', required:true, placeholder:'...' }
```

- `type`: `text` (по умолч.), `textarea`, `select` (с `options:[]`),
  `date`, `checkbox`, и др. HTML-типы.
- `required`: обязательность; может быть функцией от данных формы
  (например, e-mail в ПКЗИ обязателен, пока не отмечен чекбокс «нет E-mail»).
- `default`: значение/функция для предзаполнения при первом открытии.
- `checkbox` с `disables:'имя'` блокирует связанное поле формы.
- `showIf: d=>…`: поле видно только при выполнении условия (пересчитывается
  на каждый ввод); скрытое поле не проверяется и сохраняется пустым.

Единая карточка сотрудника (общие поля между заявками) появится вместе с
реестром сотрудников — см. «Дальнейшие шаги».

### Генерация файлов — заполнение реальных шаблонов

Готовые заявки формируются **заполнением настоящих `.docx/.xlsx`** из [types/](types/)
(точная копия официальной формы), а не пересозданием вёрстки.

- `downloadRequest(sys, data)` — берёт встроенный шаблон `window.TEMPLATES[sys.template]`,
  заполняет через `fillTemplate(...)` и скачивает как `sys.fileName(data)`.
- `fillTemplate(b64, values, textParts)` — ZIP-движок: меняет метки `{{TOKEN}}`
  в несжатых частях (`textParts`, обычно `word/document.xml`) и копирует остальные
  части «как есть». Без deflate/inflate.
- `sys.mapValues(data)` — сопоставляет поля модалки с метками `{{TOKEN}}` шаблона.

### Сборка шаблонов — `build/build.py`

Итоговый `index.html` самодостаточен, но шаблоны в него **встраиваются сборкой**:

1. `build.py` токенизирует каждый шаблон (заполняемые ячейки → `{{TOKEN}}`,
   имена токенов совпадают с `mapValues` в `index.html`).
2. Пересобирает в ZIP: `document.xml` — **STORED** (несжато, чтобы браузер менял
   метки), остальное — DEFLATE (копируется без распаковки).
3. base64 и вставляет в `index.html` между `<!--TEMPLATES:START/END-->`.

Запуск: `python3 build/build.py` (нужны `python-docx` и `openpyxl` — только
для сборки). С `file://` через `fetch` шаблоны не грузятся, поэтому base64
встроен в HTML.

### Статус шаблонов

- **Готовы:** Лаборатория ИИ (`ai_lab`), Ключевая информация ПКЗИ (`pkzi`),
  VipNet / Деловая почта (`vipnet`), Терминальный сервер (`terminal`),
  Учётная запись (`account` — головной / `account_fil` — филиал),
  Почтовый ящик (`mail_fil` — филиал), КСЭД (`ksed`).
- **В подготовке** (кнопка неактивна, статус «🛠 Шаблон в подготовке»):
  SAP (`sap`), 1С (`c1`), ВКД (`vkd`).

Заявки из `ШаблонОбщий.xlsx` (терминал, УЗ, почта) собираются общим хелпером
`build_sheet(sheet, cells, out_name)`: оставляет в книге один лист, вписывает
метки в заданные ячейки, пересобирает. openpyxl пишет строки inline, поэтому
текстовая часть для замены меток — `xl/worksheets/sheet1.xml` (не
sharedStrings). № заявки, даты и подписи бланков — от руки. Коллективные
бланки (таблица на несколько работников) оформляются на одного человека:

- **Терминальный сервер** (`terminal`, лист «6.Терминальный сервер»): бланк «на
  изменение правил работы МЭ», группа `AD_RNSK_TRM_Users_WS`; D14 — ФИО,
  E14 — наименование ПКЗИ.
- **Учётная запись** (лист «2.УЗ» головной / «УЗ (Филиал)»): поле «Офис»
  выбирает шаблон (`template` — функция от данных). Головной — домен
  rosneft.ru напрямую, бланк заодно **просит создать почтовый ящик** (E12 —
  фикс. текст), поэтому у головного отдельной заявки на почту нет; приказ о
  приёме (`showIf` — только головной) вписывается в основание D12. Филиал —
  через СИБИНТЕК (группа `PKZI_EKTS_EX_Clients_CDC`). WORKER (ФИО/должность/
  телефон одной строкой), PODR — подразделение.
- **Почтовый ящик** (`mail_fil`, лист «ПЯ (Филиал)») — **только филиал**
  (у головного почта в заявке УЗ): WORKER, SIZE (объём ящика, Гб), PODR,
  ACCOUNT (имя УЗ в домене), CERT (имя сертификата ПКЗИ), RUK (руководитель).
- **КСЭД** (`ksed`, лист «4.КСЭД») — «Управление доступом», тип
  «Первоначальный доступ» (зашит в бланке, как ДЕЙСТВИЕ/ПРОФИЛЬ/СРОК). Строка
  таблицы на одного: FIO, ACCOUNT (УЗ), EMAIL, CERT (ПКЗИ), PODR (СП), POST,
  REASON (обоснование); колонки «принимающий права» — для передачи прав, пусты.

ПКЗИ: один бланк на четыре действия — поле «Действие» (select) ставит ☒ в
нужный чекбокс шаблона (чекбоксы w14:checkbox разворачиваются в плоский текст
☒/☐ при токенизации; интерактивным остаётся только «Переименование»).
Действия поделены между карточками: `pkzi` — первичная генерация и продление
сертификата, `vipnet` — создание абонентского пункта и добавление контактов
«VipNet». Заполняются также подразделение, данные
пользователя и руководителя СП (должность/ФИО/телефон), e-mail, имя
сертификата, приказ о приёме, срок использования (два поля `type=date`,
по умолчанию сегодня → +2 года; пустая дата оставляет прочерки бланка).
Подписи — не заполняются (вписываются от руки). Тип ПКЗИ («КТ») — по
умолчанию шаблона. Обе карточки собираются фабрикой `makePkzi` (общий бланк,
свой набор действий и своя копия данных в store); `vipnet` заведена отдельно,
чтобы VipNet находился как самостоятельная система. Нюансы:

- телефоны дополняются пробелами до 28 знаков (`padTo`, ширина телефона в
  исходном шаблоне), чтобы подписи «Телефон … Подпись» строкой ниже не
  съезжали; в шаблоне на этих метках `xml:space="preserve"` (см. `build.py`);
- приказ вводится как «№ приказа, дата» (напр. `86-к, 11.12.2020`), «от»
  подставляет код (`orderFmt`) → в заявке «Приказ № 86-к от 11.12.2020»;
- чекбокс «нет E-mail» блокирует поле E-mail и снимает обязательность;
  в заявку тогда пишется «в процессе оформления»;
- имя сертификата — с новой строки после «Имя сертификата:», подчёркнутым
  («на линии»); пустое значение → линия «___» под заполнение от руки;
  при «Первичной генерации» поле скрыто (`showIf`) — сертификата ещё нет,
  введённое ранее значение при этом не сохраняется.

### Хранение и перенос данных

- `store` — объект `{ systemId: {данные полей} }`, сохраняется в `localStorage`
  под ключом `access-requests-v1`.
- `exportJson()` / `importJson()` — выгрузка и загрузка всего состояния файлом.

## Текущий набор систем

Порядок карточек (TASK_01): **Учётная запись, Почтовый ящик, ПКЗИ, VipNet ДП,
КСЭД, SAP, 1С, ВКД, Терминальный сервер, Лаборатория ИИ**.

- **Готовы** (шаблоны из [types/](types/)): ПКЗИ, VipNet ДП, Терминальный
  сервер, Лаборатория ИИ.
- **Заглушки** («Шаблон в подготовке»): Учётная запись, Почтовый ящик, КСЭД,
  SAP, 1С, ВКД.

Гейтинга (блокировки карточек по зависимостям) нет — последовательность
задаётся порядком в сетке и цветовым выделением обязательных первых заявок
(УЗ, Почта, ПКЗИ). Счётчик «Оформлено: N из M» учитывает только системы
с подключённым шаблоном.

## Две вкладки: Сотрудник / Администрирование (TASK_01)

Над вкладками — строка с «Экспорт JSON» / «Импорт JSON»: выгрузка и загрузка
данных **одного сотрудника** (его заявки, объект `store`).

### Сотрудник (`#pane-emp`, основная)

Сетка карточек всех систем — см. «Текущий набор систем». Все карточки с
шаблоном доступны сразу, блокировки нет.

### Администрирование (`#pane-admin`) — реестр сотрудников

- Кнопки: **«Импорт данных»** (JSON-файл со всеми сотрудниками → localStorage,
  с подтверждением замены), **«Экспорт»** (выгрузка реестра в
  `сотрудники_ГГГГ-ММ-ДД.json` — дата в имени, чтобы не путать версии),
  **«Добавить сотрудника»** (модалка; обычный порядок — сначала импорт,
  потом добавление).
- Таблица под кнопками: № п/п, ФИО, должность, телефон, e-mail,
  подразделение, ФИО/должность/телефон руководителя, № и дата приказа.
  Клик по строке — редактирование карточки сотрудника.
- Поля карточки — `EMP_FIELDS` (совпадают с колонками таблицы).
- Хранение: массив `employees` в `localStorage` (`employees-v1`).
  **localStorage — рабочий кэш**: переживает закрытие браузера, но теряется
  при очистке данных браузера, смене браузера/профиля/компьютера. Источник
  истины — экспортированный JSON-файл у ИТ; после изменений реестра — «Экспорт».
  Реестр — персональные данные: в git не попадает.

### Реализация

- `switchTab(name)` переключает `.tab`/`.pane` по `data-tab` / `pane-<name>`.
- `renderGrid()` рисует единственную сетку `#grid`; `renderEmployees()` —
  таблицу реестра.
- Модалка одна на два сценария: `showModal(...)` перенастраивает заголовок,
  поля и кнопку `mSave` (заявка → `saveAndDownload`, сотрудник →
  `saveEmployee`); построитель полей общий (`formHtml`).
