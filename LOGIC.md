# Логика сервиса заявок на доступы

Документ фиксирует текущую реализацию `index.html` — как всё устроено и куда вносить правки.

## Назначение

HTML-сервис для оформления заявок на доступы к корпоративным системам. Лежит на
сетевом хранилище, открывается двойным кликом (`file://`). Новый сотрудник видит
чек-лист систем, заполняет заявки и по каждой скачивает готовый файл (Word/Excel).

## Ограничения и принятые решения

| Требование | Решение |
|---|---|
| Один HTML-файл, без зависимостей | Весь HTML+CSS+JS в `index.html`, без CDN и сборки |
| Word/Excel без библиотек | `.doc` = Word-совместимый HTML, `.xls` = HTML-таблица. Открываются в MS Office |
| Отдельный файл на каждую заявку | При «Сохранить и скачать» формируется отдельный документ |
| Скачивание из браузера | `Blob` + `<a download>` |
| Хранение в JSON | `localStorage` (браузер с `file://` не пишет на диск молча) + Экспорт/Импорт JSON |

## Поток работы сотрудника

1. Открывает файл → видит **чек-лист** карточек систем со статусом
   «● Не оформлено / ✓ Оформлено».
2. Нажимает **«Заполнить»** → открывается **модальное окно** с полями.
3. Заполняет поля (обязательные проверяются) → **«Сохранить и скачать»**.
4. Состояние сохраняется в `localStorage`, файл заявки **скачивается автоматически**.
5. Заявку можно **«Изменить»** или **«Скачать файл»** повторно.
6. Прогресс отображается как «Оформлено: N из M».

## Архитектура кода (`index.html`)

Вся предметная логика вынесена в конфиг — правки идут туда, а не в код.

### `SYSTEMS` — список систем (главный конфиг)

Массив объектов, по одному на систему. Поля объекта:

- `id` — уникальный идентификатор (ключ в `localStorage`).
- `title`, `icon`, `desc` — отображение на карточке.
- `format` — `'word'` (.doc) или `'excel'` (.xls).
- `fields` — массив полей модального окна (см. ниже).
- `fileName(d)` — функция имени скачиваемого файла по данным `d`.
- `render(d)` — функция, возвращающая **HTML-содержимое файла заявки**.

**Добавить систему** = добавить объект в массив `SYSTEMS`.
Это закрывает требование «список дополнится со временем».

### Описание поля (`fields[]`)

```js
{ name:'fio', label:'ФИО', type:'text', required:true, placeholder:'...' }
```

- `type`: `text` (по умолч.), `textarea`, `select` (с `options:[]`), и др. HTML-типы.
- `required`: обязательность (проверяется перед сохранением).

`COMMON` — переиспользуемый набор общих полей сотрудника (ФИО, подразделение,
должность, телефон), подмешивается в системы через `...COMMON`.

### Генерация файлов — заполнение реальных шаблонов

Готовые заявки формируются **заполнением настоящих `.docx/.xlsx`** из [types/](types/)
(точная копия официальной формы), а не пересозданием вёрстки.

- `downloadRequest(sys, data)` — берёт встроенный шаблон `window.TEMPLATES[sys.template]`,
  заполняет через `fillTemplate(...)` и скачивает как `sys.fileName(data)`.
- `fillTemplate(b64, values, textParts)` — ZIP-движок: меняет метки `{{TOKEN}}`
  в несжатых частях (`textParts`, обычно `word/document.xml`) и копирует остальные
  части «как есть». Без deflate/inflate.
- `sys.mapValues(data)` — сопоставляет поля модалки с метками `{{TOKEN}}` шаблона.

### Сборка шаблонов — `build/build.py`

Итоговый `index.html` самодостаточен, но шаблоны в него **встраиваются сборкой**:

1. `build.py` токенизирует каждый шаблон (заполняемые ячейки → `{{TOKEN}}`,
   имена токенов совпадают с `mapValues` в `index.html`).
2. Пересобирает в ZIP: `document.xml` — **STORED** (несжато, чтобы браузер менял
   метки), остальное — DEFLATE (копируется без распаковки).
3. base64 и вставляет в `index.html` между `<!--TEMPLATES:START/END-->`.

Запуск: `python3 build/build.py` (нужен `python-docx` — только для сборки).
Токены с `file://` через `fetch` не грузятся, поэтому base64 встроен в HTML.

### Статус шаблонов

- **Готовы:** Лаборатория ИИ (`ai_lab`), Ключевая информация ПКЗИ (`pkzi`),
  VipNet / Деловая почта (`vipnet`), Терминальный сервер (`terminal`).
- **В подготовке** (кнопка неактивна, статус «🛠 Шаблон в подготовке»):
  ВКД (`vkd`).

Терминальный сервер: лист «6.Терминальный сервер» из `ШаблонОбщий.xlsx`
(остальные листы книги при сборке удаляются, openpyxl). Бланк «на изменение
правил работы МЭ», группа `AD_RNSK_TRM_Users_WS` и тексты
описания/обоснования зашиты в шаблоне. Бланк рассчитан на коллективный
доступ, но оформляем на одного человека: D14 — ФИО, E14 — наименование ПКЗИ.
openpyxl пишет строки inline, поэтому текстовая часть для замены меток —
`xl/worksheets/sheet1.xml` (не sharedStrings). № заявки, даты и подписи —
от руки.

ПКЗИ: один бланк на четыре действия — поле «Действие» (select) ставит ☒ в
нужный чекбокс шаблона (чекбоксы w14:checkbox разворачиваются в плоский текст
☒/☐ при токенизации; интерактивным остаётся только «Переименование»).
Действия поделены между карточками: `pkzi` — первичная генерация и продление
сертификата, `vipnet` — создание абонентского пункта и добавление контактов
«VipNet». Заполняются также подразделение, данные
пользователя и руководителя СП (должность/ФИО/телефон), e-mail, имя
сертификата, приказ о приёме, срок использования (два поля `type=date`,
по умолчанию сегодня → +2 года; пустая дата оставляет прочерки бланка).
Подписи — не заполняются (вписываются от руки). Тип ПКЗИ («КТ») — по
умолчанию шаблона. Карточка «VipNet / Деловая почта» (`vipnet`) — тот же
бланк через фабрику `makePkzi` с предвыбранным действием «Создание АП»,
своя копия данных в store; заведена отдельно, чтобы VipNet находился как
самостоятельная система. Нюансы:

- телефоны дополняются пробелами до 28 знаков (`padTo`, ширина телефона в
  исходном шаблоне), чтобы подписи «Телефон … Подпись» строкой ниже не
  съезжали; в шаблоне на этих метках `xml:space="preserve"` (см. `build.py`);
- приказ вводится как «№ приказа, дата» (напр. `86-к, 11.12.2020`), «от»
  подставляет код (`orderFmt`) → в заявке «Приказ № 86-к от 11.12.2020»;
- чекбокс «нет E-mail» блокирует поле E-mail и снимает обязательность;
  в заявку тогда пишется «в процессе оформления»;
- имя сертификата — с новой строки после «Имя сертификата:», подчёркнутым
  («на линии»); пустое значение → линия «___» под заполнение от руки.

### Хранение и перенос данных

- `store` — объект `{ systemId: {данные полей} }`, сохраняется в `localStorage`
  под ключом `access-requests-v1`.
- `exportJson()` / `importJson()` — выгрузка и загрузка всего состояния файлом.

## Текущий набор систем

Реализуются реальные заявки по шаблонам из [types/](types/) (решение: «только
отдельные файлы»): **Лаборатория ИИ, ПКЗИ, VipNet ДП, ВКД**.

Заявки из `ШаблонОбщий.xlsx` (Учётная запись, Почта, КСЭД, МЭ/терминал, СЭИД) —
позже. Тогда же к флоу нового сотрудника вернётся последовательность
`Учётная запись → Почта → остальное` (сейчас у всех `requires: []`).

## Две вкладки: новый / действующий сотрудник

При открытии страницы — переключатель вкладок (`switchTab`):

### Новый сотрудник (`#pane-new`, гейтинг включён)

Заявки открываются последовательно, по мере получения базовых доступов:

1. Сначала доступна только **«Учётная запись»**.
2. После её оформления открывается **«Почтовый ящик»**.
3. После почты открываются **все остальные** системы — порядок свободный.

Заблокированные карточки затемнены, кнопка «Заполнить» неактивна, статус
показывает, что нужно оформить первым (🔒 Сначала: …).

### Действующий сотрудник (`#pane-current`, без гейтинга)

Все важные данные уже есть → **все системы доступны сразу**, без привязки
к последовательности.

### Реализация

- У каждой системы есть поле `requires: [id, …]` — какие заявки должны быть
  оформлены раньше (для флоу нового сотрудника). Сейчас у всех `[]` (заявки
  account/mail появятся из `ШаблонОбщий.xlsx`); тогда будет
  `account: []`, `mail: ['account']`, остальные: `['mail']`.
- `renderGrid(containerId, gated)` рисует чек-лист в нужный контейнер:
  `gated=true` (новый) учитывает `requires`, `gated=false` (действующий)
  игнорирует их.
- `missingReqs(s, gated)` возвращает список незакрытых зависимостей; если он
  непустой и заявка ещё не оформлена — карточка заблокирована.
- Состояние `store` общее для обеих вкладок (один и тот же `localStorage`).
